# ADR 0001 — المعمارية والتقنية (Architecture & Stack)

- الحالة: مقبول
- التاريخ: 2026-06-16

## السياق

مُعين منصة تجارة وتوصيل لليمن. المتطلب الأهم من صاحب المنتج: **الثبات عند
التوسّع** (عشرات الآلاف من التجار، ملايين العملاء) و**منطق خلفي مالي سليم
100%**. يضاف لذلك واقع يمني: ضعف الكهرباء/الإنترنت، تجزئة المحافظ، وانقسام
البنية المالية شمال/جنوب.

## القرار

**1) معمارية: Modular Monolith.**
تطبيق خلفي واحد مقسّم إلى وحدات (modules) ذات حدود واضحة (auth، merchants،
catalog، orders، shipping، billing، ledger، messaging). نتجنّب
microservices مبكراً لأنها تضيف تعقيد توزيع (latency، اتساق نهائي، تشغيل)
بلا حاجة فعلية الآن. الوحدات مصمّمة لتنفصل لاحقاً عند ظهور حاجة قياس حقيقية.

**2) اللغة والإطار: TypeScript + NestJS.**
أنواع صارمة تقلّل أخطاء وقت التشغيل، وNestJS يفرض بنية وحدات منظّمة تناسب
الـModular Monolith، ومجتمعه واسع وتوظيفه سهل.

**3) قاعدة البيانات: PostgreSQL 16 + Prisma.**
نحتاج ضمانات ACID ومعاملات قوية للفلوس. PostgreSQL معيار صناعي مُثبَت عند
التوسّع. Prisma يعطي أنواعاً آمنة ومعاملات صريحة.

**4) الطوابير: Redis + BullMQ.**
محرّك المطابقة (reconciliation) ودورة الإنذار (dunning) أحداث غير متزامنة
يجب أن تكون idempotent وقابلة لإعادة المحاولة — وهذا ما توفّره BullMQ.

**5) الواجهة: Next.js كـ PWA يعمل أوفلاين.**
متطلب القسم 22 (الاستمرارية عند انقطاع الكهرباء/النت) يفرض دعماً أوفلاين-أولاً
(service worker، تخزين محلي، مزامنة عند العودة).

**6) النقود: أعداد صحيحة فقط (لا float)، وقيد مزدوج (double-entry).**
انظر ADR 0002.

## البدائل المرفوضة

- **Laravel/Django:** ممتازة للـCRUD، لكن نريد أنواعاً صارمة عبر كامل المكدّس
  (خلفية + واجهة بنفس اللغة) لتقليل الأخطاء المالية، فاخترنا TS الموحّد.
- **Microservices الآن:** تعقيد تشغيلي مبكر بلا عائد؛ نؤجّلها حتى تفرضها الحاجة.
- **MongoDB للفلوس:** نتجنّب — نحتاج معاملات قوية وقيوداً علائقية صارمة.

## النتائج

- مكدّس موحّد بلغة واحدة، سهل التوظيف والصيانة.
- مسار ترقية واضح: وحدات → خدمات عند الحاجة.
- قلب مالي معزول وقابل للاختبار وحده (packages/ledger).
